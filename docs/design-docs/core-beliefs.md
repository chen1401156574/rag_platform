# 核心设计信念

## 1. RAG 回答必须可核验

系统不是单纯聊天工具，而是基于企业知识的问答平台。回答质量不能只看语言是否流畅，还要看是否能回到原始文档、检索 Chunk、Prompt 和 Trace 节点。

落地要求：

- 回答段落带引用。
- 引用能打开来源或至少展示 Chunk 内容。
- 检索内容不足时明确说明，不伪装成完整答案。
- Trace 详情展示核心算子输入输出。

## 2. 缺参数时先追问

报销、制度、流程类问题常依赖城市、级别、时间、场景、金额、文档版本等参数。系统不应替用户补全关键事实。

落地要求：

- 检索后先做歧义审计。
- 关键参数缺失时通过 `clarify` SSE 事件返回追问。
- 用户补充后合并原问题重新检索。
- 非追问轮次和追问轮次要避免循环追问。

## 3. 管理端优先服务排障

管理端的价值是解释系统为什么这么回答，以及如何调整系统行为。

落地要求：

- 重要列表页需要筛选、排序、状态、分页和详情入口。
- Trace、入库任务、知识库 Chunk 等页面需要保留关键 ID。
- 配置页需要说明当前生效值与默认值的关系。
- 失败状态要能定位到错误信息和相关节点。

## 4. 配置应集中，默认值要可追踪

Prompt、模型、top_k、意图树、知识库绑定等运行时行为应尽量集中在系统配置或意图配置中。

落地要求：

- 默认 Prompt 写在后端服务层，并通过管理端可编辑配置覆盖。
- 意图树配置中的 `kind`、Prompt、MCP 参数模板要有明确路由语义。
- 代码兜底值必须在文档或注释中可追踪。

## 5. 文档结构服务协作

文档不追求一次性大而全，而要让后续任务快速找到正确上下文。

落地要求：

- `AGENTS.md` 做入口导航。
- `ARCHITECTURE.md` 记录系统事实。
- `docs/DESIGN.md` 记录设计约束。
- `docs/PLANS.md` 记录当前执行状态。
- 具体设计和计划放到对应子目录。
